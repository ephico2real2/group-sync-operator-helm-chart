{{- if .Values.oauthSecretExtraction.enabled }}
**OAUTH SECRET EXTRACTION ENABLED**

The chart will automatically extract the LDAP password from your existing OAuth secret
and create the required GroupSync secret. The installation order is:

1. Namespace (sync-wave: -2)
2. OperatorGroup (sync-wave: -1)
3. Operator Subscription + Job RBAC (sync-wave: 0)
4. InstallPlan approver Job, only when installPlanApproval=Manual (sync-wave: 1)
   OAuth extraction ServiceAccount/ClusterRole/ClusterRoleBinding (sync-wave: 1)
5. Operator readiness wait Job (sync-wave: 2)
   OAuth Secret Extraction Job (sync-wave: 2)
6. GroupSync CR (sync-wave: 3)

The GroupSync CRD is not in this list because this chart does not install it. OLM does, when the
Subscription at wave 0 resolves against the catalog — so it is established well before the GroupSync
CR at wave 3, and OLM stays its single owner.

{{ if .Values.crd.install -}}
crd.install is TRUE for this release, so the chart is shipping its own copy of the CRD. That is the
bootstrap escape hatch, not the steady state: it is there so a direct `helm install` onto a cluster
without the operator can resolve the GroupSync kind. Once OLM has installed the operator, set it back
to false so the catalog copy is the only one. The object is annotated resource-policy: keep and
Prune=false, so turning it off does not delete the CRD out from under your GroupSync CRs.
{{ else -}}
If a plain `helm install` on a bare cluster fails with `no matches for kind "GroupSync"`, install the
operator first, or set crd.install=true for that one install. ArgoCD never needs it.
{{ end -}}

The OAuth extraction job will:
- Extract bindPassword from {{ .Values.oauthSecretExtraction.sourceSecret.name }} ({{ .Values.oauthSecretExtraction.sourceSecret.namespace }})
- Create {{ .Values.oauthSecretExtraction.targetSecret.name }} secret in {{ .Values.oauthSecretExtraction.targetSecret.namespace }}
- Use bindDN: {{ .Values.oauthSecretExtraction.bindDN }}

For single-step installation:
  helm install {{ .Release.Name }} charts/group-sync-operator-helm --set oauthSecretExtraction.enabled=true

{{- else }}
For a new installation, it's recommended to follow this two-step process:

STEP 1: Install the operator first (without GroupSync CR)
  helm install {{ .Release.Name }} charts/group-sync-operator-helm --set groupSync.enabled=false

STEP 2: Wait for operator to be ready, then enable GroupSync CR
  helm upgrade {{ .Release.Name }} charts/group-sync-operator-helm --set groupSync.enabled=true

Alternatively, enable OAuth secret extraction for automated setup:
  helm install {{ .Release.Name }} charts/group-sync-operator-helm --set oauthSecretExtraction.enabled=true

WITH EXTRACTION OFF, THE BIND SECRET IS YOURS TO CREATE. Nothing in this release writes it, and the
operator treats a missing key as an empty string rather than an error — so wrong key names give you an
anonymous bind, not a failure:

  oc create secret generic {{ .Values.oauthSecretExtraction.targetSecret.name }} \
    -n {{ .Values.oauthSecretExtraction.targetSecret.namespace }} \
    --from-literal=username='<bind DN>' --from-literal=password='<bind password>'

The keys must be exactly username and password. The OAuth identity provider's own Secret uses bindPassword
and is not managed by this chart.
{{- end }}

VERIFICATION STEPS:
=================

1. Verify the Operator installation:
   $ oc get clusterserviceversions.operators.coreos.com -n {{ .Values.groupSync.namespace }}
   $ oc get pods -n {{ .Values.groupSync.namespace }}

2. Verify the GroupSync resource:
   $ oc get groupsyncs.redhatcop.redhat.io -n {{ .Values.groupSync.namespace }}

3. Check the GroupSync resource status:
   $ oc describe groupsyncs.redhatcop.redhat.io {{ .Values.groupSync.name }} -n {{ .Values.groupSync.namespace }}

4. View synchronization logs:
   $ oc logs -n {{ .Values.groupSync.namespace }} deployment/group-sync-operator-controller-manager -c manager --tail=100

5. Verify LDAP connectivity — use the test suite, which does exactly this and more:
   $ helm test {{ .Release.Name }} -n {{ .Release.Namespace }} --logs

   It resolves DNS, opens the port, verifies the TLS chain AND the hostname against the CA the CR
   actually loads, and confirms the operator completed a sync. A hand-rolled ldapsearch cannot:
   the operator image ships no shell utilities at all, the credentials Secret holds `username` and
   `password` rather than `bindDN`/`bindPassword`, and with groupSync.url left empty the url is only
   known after it is derived from the cluster's OAuth CR.

   The url the CR is actually using, whether you set it or it was derived:
   $ oc get groupsyncs.redhatcop.redhat.io {{ .Values.groupSync.name }} -n {{ .Values.groupSync.namespace }} \
       -o jsonpath='{.spec.providers[0].ldap.url}{"\n"}'

TROUBLESHOOTING:
==============

If you encounter issues:

1. Check that the CA certificate is correct:
   $ oc get configmap {{ include "group-sync-operator-helm.caName" . }} -n {{ include "group-sync-operator-helm.caNamespace" . }}

2. Verify LDAP credentials secret:
   $ oc get secret {{ .Values.groupSync.credentialsSecret.name }} -n {{ .Values.groupSync.credentialsSecret.namespace }}

3. Look for errors in the operator logs:
   $ oc logs -n {{ .Values.groupSync.namespace }} deployment/group-sync-operator-controller-manager -c manager --tail=100

4. Check operator events:
   $ oc get events -n {{ .Values.groupSync.namespace }}

5. If a value you changed seems to have no effect, or an upgrade fails over a value you are no
   longer passing: helm upgrade REUSES the user-supplied values from the previous revision, so
   anything once given with -f or --set keeps applying even after the chart default changes.

   $ helm get values {{ .Release.Name }} -n {{ .Release.Namespace }}          # what you supplied
   $ helm get values {{ .Release.Name }} -n {{ .Release.Namespace }} --all    # after the merge
   $ helm upgrade {{ .Release.Name }} charts/group-sync-operator-helm -n {{ .Release.Namespace }} --reset-values

   --reset-values discards ALL remembered values, so re-pass any you still want.

6. For additional help, see the documentation:
   https://github.com/redhat-cop/group-sync-operator
